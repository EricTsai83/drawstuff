# 18A — 共編儲存 UX 與本機快取邊界

- 狀態：規劃中，尚未實作；2026-09-23 自原 Plan 18 §3.6 拆出為獨立計畫。
- 目的：讓共編模式下的每一個儲存入口都明確指出「存到哪裡」，並停止把房間畫布寫進個人場景的本機快取。
- 前置：**無**。本計畫不依賴 [18B](18b-collaboration-authority-reset.md) 的授權權威重置，
  也不依賴 [18C](18c-collaboration-surface.md) 的列表與告知，可在現有 DB 權威架構上獨立實作與驗收。
- 本文件描述目標，不代表目前按鈕或快取行為。

## 0. 兩個與其他計畫不同的前提

**這是唯一一個「共編資料可全刪」幫不上忙的計畫。** 18B 的破壞性重置前提來自「共編資料都是測試資料」；
本計畫動的卻是**必須保住的那一份**——個人場景的 localStorage 快取、`currentSceneId` 與 revision。
所以這裡沒有「刪掉重來」這個選項，§4 的恢復契約要逐條驗證。

**這是最不受 Neon 額度用盡影響的計畫。** 它幾乎全部是 client 行為：localStorage 寫入者、
儲存入口的模式判斷、快捷鍵協調、離頁提示。既有的 jsdom／元件測試與 PGlite（見
[18B §0.4](18b-collaboration-authority-reset.md)）足以驗收絕大部分，**因此在 DB 額度恢復之前，
這是進度最不受阻的一份工作，應該優先做。**

## 1. 為什麼先做這一項

現況 `apps/web/src/hooks/excalidraw/use-collaboration-room.ts` 以 `ownsCanvas && !currentSceneId`
決定是否暫停一般本機快取：**有個人 sceneId 的共編使用者，房間畫布仍會被寫進個人場景的
localStorage**（elements、appState、files 的 JSON），只有沒有 sceneId 的訪客才暫停，訪客另存後又恢復。

這是現在就存在的行為，不需要等待任何架構遷移就能修。把它綁在多階段的授權權威遷移之後，等於讓一個
可以獨立驗收的資料邊界問題，跟著一個需要原型驗證與權威重置的大工程一起延後。

同時，共編下的「儲存」目前沒有清楚的目的地語意：個人場景、房間快照、瀏覽器快取與下載檔案是四種
不同結果，UI 不可統稱「已儲存」。

## 3. 模式、目的地與操作

共編快照屬於房間，所有成員共用；不是按 user 各存一份。自動保存的是可恢復的房間畫布密文，不是每筆
訊息立即持久化。

| 情境／入口                 | 用語與行為                                                             | 儲存目的地                                 |
| -------------------------- | ---------------------------------------------------------------------- | ------------------------------------------ |
| 個人雲端場景               | 「儲存至我的場景」，更新目前場景；未建立時沿用命名介面                 | 使用者的個人雲端 scene                     |
| 共編房間                   | 常駐「房間自動保存中／房間已保存／房間保存失敗」；斷線或待同步另行標示 | 房間共用加密快照                           |
| 共編另存個人雲端           | 「另存至我的場景…」，沿用命名／位置介面，明確建立新副本                | 新的個人 scene，不覆寫原場景               |
| 共編下載                   | 「下載本機副本…」，沿用檔案匯出流程                                    | 使用者下載的檔案，不是 localStorage        |
| 由自己的場景開房後回寫原稿 | 獨立入口「更新我的原場景〈名稱〉」，僅有權限且來源關聯有效者可用       | 明確指定的原 scene，沿用 revision 衝突保護 |

- 編輯器常駐區分「個人場景」與「共編房間」，保留房間名稱／身分及儲存目的地。房間已保存不得被個人副本的
  成功 toast 取代；個人副本存好也不能讓房間未保存提示消失。
- 個人模式 Ctrl/Cmd+S 維持雲端儲存；房間模式對應房間保存／重試，不能暗中建立或覆寫個人 scene。接入既有
  快照寫入者協調與去重，不讓每位成員繞過排程競相上傳；唯讀使用者不可藉快捷鍵寫入。無待存變更時只呈現
  現有確認狀態。
- 「房間已保存」必須對應涵蓋目前需保存變更的持久化確認；WebSocket 已送出、收到他人畫筆或較舊版本快照
  成功，都不足以宣告目前畫布已保存。失敗保留待存狀態並可重試；離頁有未保存變更時提供遺失風險提示，
  不依賴 unload 網路請求保證成功。
- 另存捕捉當下的一致畫布與附件，成功後仍留在房間，可提供「開啟副本」連結；不得切換共編畫布的
  `currentSceneId`／權威，也不讓後續房間修改自動回寫副本。開啟副本使用另一分頁，或依明確離房流程切換。
- 個人副本的附件必須有獨立可用的儲存生命週期，不依賴會被房間刪除的密文物件。既有來源 scene 的退休關係
  維持現況；新副本不新增會連帶關房的關聯。
- 沿用既有命名、匯出與衝突處理介面，不為每次存檔增加確認彈窗或同意勾選。在共編另存介面顯示
  「共編房間仍維持加密；個人雲端副本不採端對端加密」，下載介面說明檔案未加密。個人副本不採 E2EE
  不代表公開。完整的全產品加密告知屬於 [18C](18c-collaboration-surface.md)；本計畫只負責共編入口本身的目的地與保護範圍說明。
- 不得只改按鈕文案而保留舊的 `currentSceneId` 自動更新分支。正常個人模式的既有保存能力保留。

### 3.1 跨成員保存確認與重試

這不是只有 UI 文案的工作。現有 `snapshot-cadence.ts` 的 writer 本地成功回應與
`noteSnapshotWritten()` 大小超限解除訊號，不足以代表所有成員的目前畫布已保存。

- 為一次捕捉的快照固定保存識別、generation、內容摘要與確認涵蓋範圍；將成功確認綁定實際持久
  revision／checksum。不能僅因 DB revision 增加就清除本機 dirty；A 存的是舊快照時，B 的新編輯仍未保存。
- 固定可驗證的涵蓋演算法與事件格式：例如由 client 對照已持久快照的內容摘要／元素版本，
  無法證明涵蓋目前內容就保持未確認，必要時讀取已保存快照核對。合併衝突與刪除元素也須納入。
  明文摘要若需跨成員傳送，走房間加密訊息；不為此上傳明文內容或可推測內容的額外 metadata。
- Writer 成功後通知其他成員；通知須能與可信的持久結果核對，不能只信任 peer 自稱已保存。
  漏通知／重連可查目前快照或操作結果恢復，不新增每筆畫筆的 DB 查詢，也不要求其他成員重傳整份快照。
- 非 writer 的 Cmd/Ctrl+S 發出可合併的保存請求，由目前 writer 排程；writer 失聯時沿用選舉接手，
  timeout 與失敗保持未保存。快捷鍵不可直接套用會繞過選舉的離房 force flush；唯讀只查看狀態。
- 保存捕捉後又發生新編輯，舊 ACK 只能確認其捕捉範圍；重複、亂序與上一連線 ACK 不可誤清新 dirty。
  附件尚未持久可恢復時，不得宣稱整份畫布已保存。
- 18A 可在目前 DB 權威上交付上述契約；18B 必須保持同一產品語意，接上其 operationId 查詢／取消機制。

目前 `SNAPSHOT_INTERVAL_MS` 是 30 秒，這只是排程間隔，不是資料遺失上限；網路或保存失敗會延長窗口。
**已確認保存的內容必須可恢復；未確認內容在最後持有者的瀏覽器退出後可能遺失。**
首版不承諾「伺服器收到意圖後，瀏覽器關掉仍保證存完」或離線重載恢復。顯示最後確認狀態、
未保存／失敗與離頁提示；不以 unload 上傳保證成功。驗收分開量測保存請求延遲與編輯到持久確認的等待時間。

## 4. localStorage 與恢復

改為一致規則，取代現有的 `ownsCanvas && !currentSceneId` 條件：

- 畫布歸房間所有期間，不論房主、訪客、有無來源 sceneId、是否已另存副本，都不自動把房間畫布／圖片寫入
  一般個人場景 localStorage，也不改以 IndexedDB 等方式偷偷保留房間內容。房間編輯使用記憶體與遠端加密
  快照；本階段不承諾離線重載恢復未上傳變更。
- 入房前保留原個人草稿及其 sceneId／revision；進入、退出、初始化失敗、撤權、重載、登出及多分頁切換均要有
  明確恢復契約。暫停與取消已排程的 debounce、卸載保存、遠端 hydration 等寫入，須在房間內容套入前生效，
  不能只靠較晚的 React effect。
- 重載房間先重新授權並取得有效房間快照；不得把舊個人快取送進房間。缺鑰、失聯或讀取失敗不得以空畫布／
  舊快取冒充房間內容。退出房間先切回正確個人畫布，再恢復其快取寫入。
- 「更新我的原場景」成功後同步更新其獨立快取／revision 或使舊快取失效，恢復時重新載入，不能只停用原有
  快取鎖，導致下次用舊資料覆蓋新雲端版本。另存副本只處理該次明確儲存結果，不把房間後續 `onChange`
  綁到副本。
- 保留個人草稿不得因入房而清空；多分頁的個人場景快取不得被共編寫入污染。實作前必須驗證目前共用 storage
  key 與 sessionStorage 房間標記的恢復路徑，再固定所需的隔離識別。
- 上述限制針對畫布內容。語言／UI 偏好、分頁房間識別是不同資料；不宣稱房間「完全不在本機留下資料」。
  下載檔案與個人副本須由明確操作產生。本機金鑰記憶屬於 [18C](18c-collaboration-surface.md)，不在本計畫範圍。

## 5. 實作順序

1. 盤點所有本機快取寫入者（debounce、unload、hydration、多分頁同步）與所有共編可觸及的儲存入口
   （工具列、主選單、雲端存檔對話框、快捷鍵、另存／複製、離頁提示、背景保存），固定模式／目的地判斷的
   單一來源，不讓各入口各自判斷。
2. 先實作快取隔離與恢復契約，驗證入房／重載／離房／撤權／登出／多分頁，以及原 scene 快取失效路徑，
   避免停寫造成舊資料回灌。
3. 固定並實作 §3.1 的跨成員確認／writer 請求與接手契約，再接模式化入口、常駐狀態與快捷鍵。
4. 完成另存、下載與更新原稿三個入口的獨立生命週期與權限／revision 檢查。

## 6. 驗收矩陣

| 情境                     | 必須證明的結果                                                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 儲存 UX／快捷鍵          | 所有共編存檔入口明確區分房間、另存與更新原稿；Ctrl/Cmd+S 不寫個人 scene，唯讀不能寫房間；舊快照 ACK 不誤報新變更已保存                       |
| 跨成員保存確認           | A 保存時 B 繼續編輯、ACK 亂序／重複／遺失、writer 離線接手均不誤清 dirty；非 writer 快捷鍵不競相上傳，附件未完成不宣稱已保存                 |
| 共編另存／下載／更新原稿 | 副本資料與附件可獨立恢復；另存後留在房間且不背景回寫副本；更新原稿驗證權限與 revision；各目的地狀態與加密說明一致                            |
| 本機快取與重載           | 房主／訪客／另存後均不自動快取房間內容；涵蓋 debounce、unload、hydration、多分頁、離房／撤權／登出；原草稿保留，舊快取不覆寫新原稿或灌入房間 |
| 保存失敗／離線           | 未確認變更不顯示已保存，有重試與離頁提示；重載不承諾恢復記憶體中的未上傳內容，缺鑰／斷線不以空畫布覆寫                                       |
| 原存檔生命週期           | 個人白板與共編快照仍不互相覆寫，圖片引用與清理一致                                                                                           |
