# 20 — 以 passkey 保護的房間金鑰庫（未來最佳化）

- 狀態：未排程；2026-10-09 依擁有者要求記錄為 [19](19-server-room-key-custody.md) 之後的最佳化方向，未授權實作。
- 前置：[19](19-server-room-key-custody.md) 完成（服務端保管金鑰與列表重開已上線）。
- 目的：在保留「任何裝置都能從列表重新開啟房間」的前提下，讓服務端不再能解密房間內容，使產品可以重新誠實地宣稱端對端加密。

## 0. 概念

passkey 是以公開金鑰密碼學取代密碼的登入憑證（WebAuthn／FIDO2），私鑰存在使用者裝置或密碼管理器（iCloud 鑰匙圈、Google 密碼管理工具、1Password 等），以 Face ID／Touch ID／螢幕鎖解鎖，並由平台跨裝置同步。WebAuthn 的 **PRF extension** 讓網站在使用者驗證時，從 passkey 衍生一段只有使用者端拿得到的秘密。

做法：每位使用者有一把隨機的**金鑰庫金鑰（vault key）**；房間金鑰以 vault key 包裝後存在服務端；vault key 本身再以 passkey PRF 衍生的金鑰（以及恢復碼）包裝。服務端只保存兩層包裝後的密文，沒有任何一層的解開能力。這與 1Password（Secret Key）、Signal（PIN + SVR）、WhatsApp 加密備份與 Bitwarden 的 passkey 解鎖屬於同一類設計。

## 1. 範圍（草案）

納入：

- passkey 註冊（含 PRF）與每個 session 的金鑰庫解鎖；支援多把 passkey。
- 恢復碼：建立金鑰庫時產生，作為遺失所有 passkey 時的唯一復原途徑。
- 房間金鑰以 vault key 包裝存放（每位成員各一份），列表開房改由本機解開。
- 逐房間或逐帳號關閉 19 的服務端保管：關閉後刪除服務端包裝、恢復端對端加密宣稱。
- 不支援 PRF 的瀏覽器或驗證器：改以使用者自設密語（Argon2id 衍生）或維持 19 的服務端保管。

不做：

- 不取代目前的 Google 登入；passkey 只用於金鑰庫解鎖。
- 不提供營運者復原使用者金鑰的後門。

## 2. 待研究與決定

- 瀏覽器與密碼管理器的 PRF 支援度、跨平台同步（Apple／Google／第三方）與降級路線。
- 成員之間如何分發房間金鑰：成員加入時由已解鎖的成員以接收者公鑰封裝，或在 19 的過渡期由服務端轉交後立即改存成員金鑰庫。
- 重設連結（rotation）後如何把新金鑰重新包裝給所有成員。
- 遺失 passkey 與恢復碼的使用者體驗與資料不可逆的告知。
- 遷移：19 已保管的房間如何讓每位成員搬進自己的金鑰庫，再刪除服務端保管。
- 金鑰庫存放位置（Neon 新表或 Room DO）、配額與清理。

## 3. 風險

- 使用者多一個設定步驟（建立 passkey、保管恢復碼）；未設定者仍依賴 19 的服務端保管。
- 恢復碼遺失且 passkey 全數遺失時，房間內容永久無法開啟。
- 實作與安全審查成本高，需獨立的威脅模型更新與正式驗收。
