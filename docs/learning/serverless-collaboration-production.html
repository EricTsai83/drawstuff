房間獨立運作，列表與畫布仍留在 DB

Drawstuff 是多人協作白板。房主建立房間、分享完整連結；成員登入並通過授權後加入，日後可以用同一連結回來。目標設計也提供「我的房間」，讓使用者找到自己建立或加入的房間。瀏覽器負責共編內容的加解密，後端保存與轉送密文。

假設房主 A 與成員 B、C 正在畫圖。現況由 Neon PostgreSQL 保存 C 的權限，再通知 Cloudflare 的房間 DO 停止 C 的 WebSocket 收發。兩個服務之間可能斷線，所以 DB 還保存一份 outbox（持久待辦），每分鐘掃描並重送。這讓漏送可以恢復，卻也讓沒人在使用時仍有 DB 查詢。

目標方案把房間權限的最終決定權移到 Room DO，讓它同時知道誰有權限、誰正在連線。Neon 不需要因此退出系統：個人白板、共編密文快照及房間列表仍留在原本適合查詢與儲存的位置。

最終責任分工
位置保存或處理什麼為什麼放這裡
瀏覽器明文畫布、房間秘密、加解密後端不持有共編解密金鑰。
Room DO＋SQLite房間狀態、owner、成員角色、撤權、連線與待辦同一個房間在同一處判斷與執行授權。
Neon帳號、我的房間列表、個人白板、共編加密快照、生命週期登記沿用現有 SQL 查詢與持久儲存。
UploadThing加密圖片與附件沿用既有檔案服務，不同時進行儲存遷移。
Lifecycle DO帳號／白板退休的操作進度跨多個房間的刪除失敗後，能繼續完成。

Room DO 是每房間一個，Lifecycle DO 按退休主體分割；不是讓全站通過一個全域 DO。Cloudflare 官方也建議按房間、文件等需要協調的單位分割，但並未提供可直接取代產品需求的完整權限系統。官方設計原則。

實線代表請求／資料流，虛線代表背景觸發。箭頭不是單一請求的完整執行順序。窄螢幕可左右捲動圖表。

兩圖皆以 Next.js 部署於 Vercel 為前提。Room DO 沒有公開 HTTP 入口，因此 Next.js 的撤權、房間管理與內容授權請求，均先經 HTTPS 到 Gateway Worker，再由 Gateway 透過 DO binding 呼叫房間 RPC；瀏覽器 WebSocket 則由 Gateway 透過 binding 轉交升級請求。目前 Gateway 與 Room DO 位於同一個 Worker 部署中。

目標圖中 Room DO 呼叫 Next.js 內部儲存 adapter，則是另一方向的內部 HTTPS API 呼叫，必須驗證服務身分，並帶上 operationId 與版本資訊；不是跨執行環境直接呼叫 JavaScript 函式。

為讓主圖容易比較，兩圖省略限流、個人白板細節與刪除清理分支；附件箭頭表示授權／儲存責任，不表示所有 bytes 都經過同一 API。目標的 Lifecycle DO 另外承接帳號／白板退休，先凍結新活動，再逐房間確認撤權，最後清理 Neon 與附件；它不處理每筆畫布訊息。

為什麼選混合架構，而不是另一個極端

選項適合之處本次取捨
保留 DB 權限＋outbox既有流程成熟，跨資源 SQL 權限易管理。仍有 DB → DO 通知落差與背景掃描。
DO 權限＋Neon 內容／列表房間內授權集中，保留既有儲存與查詢。選定方案；要支付內容屏障、投影與遷移複雜度。
房間資料全部搬到 DO更多操作可以本地完成。涉及畫布儲存遷移及列表索引，不是本次必要範圍。
Redis marker 決定是否查 DB表面上能減少輪詢。commit 後、marker 前 crash 可漏提示；不能用快取是否存在判斷沒有安全待辦。

tldraw.com 的公開程式由 PostgreSQL 的分享設定／群組角色影響授權，Processor DO 讀取 outbox 再通知房間，並有 30 秒掃描補救。它是可靠交付的參考，不是「房間 DO 獨立管理全部權限、讓 DB 閒置」的同一方案。Processor 原始碼、房間 DO 原始碼。

原始碼能說明它怎麼做，不能證明團隊為何這樣選。群組關係較多、DB 本來就繁忙是可能理由，並非已確認的選型動機，也不代表掌握其線上版本與帳單。

不要只為了「用 DO 比較新」採用這個方案。如果產品高度依賴跨房間 SQL 權限、DB 原本就一直忙，或無法負擔儲存屏障與資料遷移，保留原架構可能更容易驗證與維護。Drawstuff 選擇此方向，是因房間可獨立決策，且希望減少低流量時的空查詢。

先證明邊界，再停止舊安全網

這項遷移的最大風險不是 SQL 多幾列，而是新舊權限同時生效，或有內容入口繞過 DO。因此先驗證快照屏障、附件授權與帳號退休的競態，再逐房間匯入、切換權威版本。所有舊 pending、退避與失敗工作完成或被明確接管後，才能關閉原分鐘 cron。

短暫凍結單一房間與重新連線是可接受的遷移代價。回滾不能直接讓舊 DB 角色重新授權，必須接回 DO 的最新撤權與待辦，保留相同房間秘密和可解密的資料格式。

驗收分成三件事：授權正確（踢人、重啟、舊憑證與資料入口）、恢復可靠（crash、重送、亂序與跨房間刪除）、閒置改善（無工作時沒有這條背景 DB 查詢，並量測完整成本）。前兩項通過，不等於已經省錢；費用下降，也不能替代授權驗收。
