責任分工：誰能看到明文，誰只能搬 bytes

整份契約的骨架是一句話：明文只存在於瀏覽器。其他每個元件都被刻意設計成「即使被完全觀察，也讀不懂畫布」。

元件負責什麼刻意不負責什麼
瀏覽器明文畫布、加解密、官方語意的 reconcile—
@drawstuff/collaboration與傳輸無關的訊息定義、驗證、密碼學、排序、join barrier、離線佇列與 recovery policy不知道自己跑在哪一種傳輸或哪一個 app
apps/web把上述契約綁到已驗證身分的 room API 與編輯器—
relay（Worker ＋ Durable Object）驗 token、路由、有界 fanout從不持有房間金鑰，因此無法解密；也不持久化內容（只 import server-safe 的協定入口）
Upstash Redis只存會過期的限流視窗狀態不接觸房間金鑰、明文、密文快照、附件 bytes 或儲存 capability
PostgreSQL／物件儲存唯一的持久協作資料來源—

值得學的是這些「不負責」各自靠什麼保證，因為它們的強度並不相同。

relay 讀不懂畫布，靠的是它從不持有金鑰。房間金鑰只存在於 URL fragment 與瀏覽器記憶體，不隨任何請求送出，所以 relay 收到的就只是密文——這是威脅模型 T2 的保證，屬於密碼學層級。「只 import server-safe 的協定入口」不是這個保證的來源：AES-GCM 是公開演算法，任何人只要拿到金鑰，自己寫一份解密程式就能讀。匯入邊界是另一種東西——架構約束：它讓「不小心在 relay 側解密」在結構上做不到，也讓「relay 到底需不需要金鑰」這個問題在每次 review 都有明確答案。一個防對手，一個防自己人失手，不能互相取代，也不該被寫成同一件事。

Redis 那一列是第三種保證：它確實收得到使用者與房間識別碼（那是計數器的 key），所以保證來自契約明文列出它收不到什麼。把「這個依賴看得到什麼」寫下來，比事後從程式碼推斷可靠得多。

另外兩條資料分流也是刻意的：presence 與 scene 走不同通道（presence 是易失的，壓力下可以丟；scene 在同一個 socket session 內可靠），而二進位附件 bytes 從不放進 scene 訊息裡。

授權撤銷與密碼學撤銷是兩件事

契約把這兩者分開寫，因為它們的能力邊界完全不同：把成員移出名單，擋得住他未來的存取，但無法從他腦中抹掉已經學到的金鑰。

所以真正的密碼學撤銷是世代輪替：換頻道、換金鑰衍生的 salt、換 verifier、換持久資料的世代。但要注意輪替本身也不是密碼學撤銷的全部——salt 是公開的，只有在同時換一把新的房間金鑰、且只交給留下來的成員時，讀取能力才真的被收回。可轉移的完整論述見 E2EE 與金鑰生命週期與共享金鑰架構導讀。

與之配套的是 key-check：房間列上存一個固定大小的加密檢查值，client 在接管或清空畫布之前、以及請求 join token 之前先驗它。缺少檢查值時 fail closed，伺服器也拒發 token。這樣一條錯誤的連結會在動到使用者畫布之前就停住，而不是先清空畫布再發現開不了。

還有一個容易略過的細節：錯鑰的判定是聚合的，而不是單筆失敗就下結論。連續失敗且沒有任何一次成功，才在在途的那批訊息塵埃落定後判定房間不可讀；只要有一次成功開啟，就永久解除該傳輸的這個判定。目的是避免個別損毀的訊息把使用者推進「空房間」的錯誤結論。

為什麼授權變更與它的強制執行必須同一個交易

「移除成員」其實是兩個動作：改資料庫裡的授權狀態，以及去把對方已經連上的 socket 關掉。前者在自己的資料庫裡，後者在另一個服務上。如果分兩步做，總有一個中間狀態是「已經沒有權限，但還連著」。

契約的做法是：房間變更路徑鎖住房間列、重新評估授權、把強制執行的意圖寫進 durable control outbox、然後在同一個交易裡 commit。授權狀態與它的執行意圖因此不可分割——要嘛都成立，要嘛都不成立。commit 之後才做一次同步的 best-effort 派送，只為了讓 UI 快速回應；派送失敗的留在 outbox 由獨立排程重送。

由此得到的最重要的產物是誠實的回應語意：mutation 的結果區分 enforced（Durable Object 已確認關閉 socket）與 pending（已提交、稍後強制）。pending 不是「成功」的同義詞，UI 不能把它顯示成已完成。很多系統在這裡選擇含糊，代價是使用者以為踢人已經生效。

投遞端的設計也值得看：派送是 revision-max 冪等的，所以超時後重送永遠安全；閘道回傳一個明確的拒絕碼時當作確定性拒絕直接判定失敗，其餘所有非 2xx、超時與傳輸錯誤都保持可重試。把「確定不會成功」與「這次沒成功」分開，重試才不會變成無止境地撞同一面牆。可轉移的 pattern 見 transactional outbox。

兩邊各自部署：把版本落差當常態而非缺陷

apps/web 與 Worker 都從 main 自動部署，落地時間差幾分鐘。所以每次協定版本升版之後，必然有一段時間是其中一邊比另一邊新。

契約沒有用「部署時請注意順序」來解決，而是把它做成協定的一部分：版本不符的 join 用專屬的關閉碼拒絕（不是通用的協定違規），關閉原因同時寫出兩邊的版本，讓落差在關閉紀錄裡直接可見。client 把這個拒絕讀成部署時差而非缺陷，在一個有界的時鐘視窗內退避重試，而且這段重試記在該視窗的帳上、不吃掉一般的重試預算；視窗關閉後才變成終端錯誤，補救方式是重新載入——對應的正是「分頁在升版期間一直開著」這個情境。

結論是：協定升版不需要 web 與 Worker 之間有任何部署順序要求。這是把維運限制轉成協定設計的好例子。

加入順序：先訂閱再載入，claim 最後才成立

兩個順序在契約裡被寫成硬性要求，因為反過來做會產生難以察覺的資料遺失。

第一，先訂閱再載入 baseline。加入時先訂閱，收到的 scene 訊息暫存在一個有界的 join barrier 裡，同時讓「某個 peer 提供的快照」與「持久快照」賽跑，第一個有效的 baseline 獲勝，然後緩衝的訊息依序回放並 reconcile。契約明寫 client 絕不可以先 fetch 再 subscribe——那樣做，兩個動作之間抵達的所有編輯都會憑空消失。

第二，claim 畫布是最後一步。加入房間會取得這個分頁的畫布所有權，提交順序是：驗金鑰 → 處理本地草稿並清空畫布 → 換 token 並確認世代沒變 → 最後才 claim 並開 socket。因此一個被拒絕的加入、耗盡的重試或世代競態，都不會留下任何協作 claim；而 claim 之後才失敗的話，該路徑會立刻釋放 claim 與所有半成品資源。

另一個細節值得單獨記住：定期與離開時的快照 flush，會在等待任何東西之前就先評估守衛條件並擷取畫布。因為拆除流程會在同一個 tick 關閉傳輸，而寫入要走網路——一個在 await 之後才檢查的守衛，會否決掉那一次唯一能保住房間最後編輯的寫入。

還有一個誠實的界線：畫布準備是使用者核准過的提交。若使用者選擇捨棄本地草稿而後續加入失敗，系統不會把捨棄掉的畫布重建回來。

契約裡的誠實條款

最後一章「Current operational boundaries」列的不是功能，而是已知的不足：部分 SLO 已定義但沒有任何 telemetry 承載因此無法評估；直接切換沒有 Node fallback 也沒有百分比 rollout，全域的 create/join kill switch 就是事故邊界；沒有 staging、沒有正式容量 load test、沒有完整 incident runbook。

這些被明確標示為「目前這個個人營運、有限公開測試服務可接受的營運限制」。把可接受的限制寫進契約，讀者才不會把沉默誤讀成「這部分沒問題」。
