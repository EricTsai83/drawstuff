瀏覽器端 E2EE：以 Excalidraw 理解共享金鑰架構

讓伺服器負責路由、轉發與儲存，讓參與者的瀏覽器持有解密能力。本文從共享白板出發，說明這個 pattern 的成立條件、Excalidraw 的實作，以及把它搬進有帳號與權限的產品時需要補上的設計。

學習文章・可轉移 pattern 解說，非本專案現況清單。資料查核基準：2026-09-22（上游連結已釘選 commit）。本專案現況契約見文末既有文件與圖。

架構模型上游實作產品化既有文件與圖

先確定你要保護什麼

Alice 想把一張白板分享給 Bob，兩人會同時修改，也希望重新開啟連結時找回內容。服務必須傳遞更新、保存場景與圖片，但產品要求資料庫或 relay 的被動觀察者不能讀懂畫布。這是本文的運作條件；如果產品原本就必須在伺服器處理明文，應先重新確認需求。

只用 HTTPS 能保護傳輸途中；資料抵達伺服器後仍可被讀取。伺服器管理金鑰的磁碟加密能降低儲存媒體外洩的影響，但應用服務通常仍有解密能力。端對端加密（E2EE）則把加解密放在參與者端，伺服器收到的是密文，而且不持有內容金鑰。

代價隨之出現：伺服器不能直接合併畫布語意、搜尋文字或產生明文縮圖；分享金鑰、同步衝突、錯鑰處理與金鑰遺失都必須另行設計。E2EE 是一條資料與信任邊界，不是一個加密函式就能完成的功能。

Pattern：共享解密能力，基礎設施只處理密文

Alice 的瀏覽器產生隨機金鑰 K，將它交給 Bob；兩端使用同一把 K。roomId 負責定位房間，K 負責讀懂內容，兩者責任不同。這個模型可稱為「共享金鑰的 capability link + opaque relay」：完整連結攜帶解密能力，relay 只搬運不透明的資料。此處 capability 指「持有秘密就具備某種能力」，opaque 指伺服器不解析內容。

這張圖的「伺服器只見密文」特指內容。基礎設施仍能看見路由識別、連線資訊、資料大小與時間。E2EE 不會自動隱藏誰在什麼時候參與，也不保證服務可用性。

URL fragment 是分送金鑰的容器

Excalidraw 協作連結採用 https://excalidraw.com/#room=ROOM_ID,KEY。瀏覽器載入頁面的 HTTP 請求不包含 # 後面的 fragment；頁面 JavaScript 再讀取它，將 roomId 送往 relay，但不將 KEY 放進協作請求。fragment 的規則可參考 URI fragment 說明。

因此「fragment 不會隨頁面請求送出」不等於「它不可能外洩」。頁面程式、瀏覽器擴充套件、剪貼簿、瀏覽紀錄與接收完整連結的人可能接觸它。錯誤追蹤、分析 SDK 與 log 也不能收集完整 location.href。Base64URL 只是金鑰的文字編碼，沒有再次加密。

AES-GCM 解決機密性與竄改偵測

AES-GCM 是具驗證能力的對稱加密（AEAD）。每次呼叫以 K、IV 與明文產生密文及驗證標籤；接收者用相同 K 與 IV 驗證並解密。IV 是每次加密的 nonce，不需要保密，可以與密文一起傳送，但同一把金鑰下不可重複使用。

驗證失敗時不能把密文當明文，也不能把無法解密的存檔當成空白場景覆寫。AEAD 可以偵測錯鑰或資料遭竄改，但不能單靠解密錯誤辨認是哪一種情況；它也不會自動阻止舊的有效密文被重播。

Excalidraw 實際怎麼做

以下依 2026-09-22 重新抓取的開源 master 原始碼整理，並以 commit 連結固定證據。範圍是 Excalidraw 開源 app 與 excalidraw-room relay；不是 Excalidraw+ 的私有部署保證，也不代表只安裝 editor 套件就取得完整協作服務。

資料路徑端點與伺服器的分工
即時協作Portal 將 payload 序列化並加密，以 Socket.IO 傳 roomId、密文與 IV。relay 原樣轉發；接收端 Collab 解密後再處理場景更新。
協作存檔瀏覽器把 elements 加密後存入 Firestore；外層包含 sceneVersion、ciphertext 與 iv。既有存檔的解密、reconcile 與重新加密發生於瀏覽器的 transaction callback。
圖片資產FileManager 將圖片 dataURL 與內容 metadata 打包、壓縮後加密，上傳 Firebase Storage；協作使用 roomKey。
靜態分享exportToBackend 產生新的分享金鑰，壓縮並加密場景與相關圖片。回傳分享 ID 後組成 #json=ID,KEY，與持續同步的 room 連結分開。

可追到函式的實作證據

  • encryption.ts：generateEncryptionKey 透過 Web Crypto 產生可匯出的 AES key，輸出 JWK 的 k；getCryptoKey 以 A128GCM 匯入。constants.ts 定義 ENCRYPTION_KEY_BITS = 128。
  • encryptData 每次呼叫 createIV，透過 crypto.getRandomValues 產生 12 bytes（96 bits）IV，再呼叫 subtle.encrypt。這條 helper 沒有指定 AAD，也未指定 tagLength，使用 Web Crypto 的預設 128-bit tag。
  • data/index.ts 的 generateCollaborationLinkData 產生 roomId 與 roomKey；getCollaborationLink 組成 fragment。這是預先共享秘密的連結模型，不是參與者互相做公開金鑰握手。
  • Portal.tsx 的 _broadcastSocketData 加密 JSON；Collab.tsx 的 decryptPayload 解密，client-broadcast handler 再交給場景合併邏輯。
  • relay src/index.ts 的 join-room 接受 roomId；server-broadcast 轉發 encryptedData 與 iv。這些 handler 未實作 Drawstuff 的登入 token、角色與世代授權。
  • firebase.ts 的 saveToFirebase 在 client 端讀取舊密文、解密、合併，再寫入新密文。Firestore 協調 transaction；它不需要理解 elements。
  • FileManager.ts 與 encode.ts 顯示圖片、內容 metadata 先打包，再 deflate、AES-GCM 加密。格式版本／壓縮方式等外層 encoding metadata 與 IV 仍可見；不是所有 metadata 都被隱藏。

這裡最值得移植的分工是：內容語意留在 client，持久化的一致性與轉發留在 infrastructure。端到端加密不必要求 WebRTC 或純 P2P，也不必放棄 transaction；只是伺服器的 transaction 操作對象成為不透明的密文。

128-bit 是此版本 Excalidraw 的事實，不是本文要求所有產品固定採用的位元數。Drawstuff 協作的 root key 是 32 bytes，還有用途衍生；不能把兩套實作的參數混用。上游也保留 legacy 分享格式解碼分支，其中有固定 IV 的相容處理；新的格式應遵守每次加密的新鮮 IV 規則。

搬進有權限的產品：再補上四份契約

如果 Alice 的白板屬於一個長期存在的團隊，有 owner、editor、viewer，也需要撤銷成員，就超出了「知道連結即可合作」的最小模型。下面是可移植的設計建議；不是宣稱 Excalidraw 上游已實作全部機制。

1. 把 API 授權與解密能力分開

後端用帳號、ACL 與短效 token 決定誰能連線、下載或寫入；瀏覽器用 K 決定能否解密。token 綁定資源、角色、有效期與授權世代。不要把內容 key 塞進 token，也不要把「可解密」當作已通過寫入授權。

例如 viewer 即使持有對稱金鑰，在密碼學上仍有製造有效密文的能力，所以「只能讀」需要伺服器強制控制寫入入口。共享 key 也無法證明訊息由特定成員產生；需要可驗證作者時，必須另外設計身分與簽章。

2. 為金鑰、用途與資料格式分工

需要隔離 realtime、snapshot、asset 的生命週期時，可以用 HKDF（以既有秘密衍生金鑰的標準函式） 從 root key 衍生用途金鑰，將 room、generation 與 purpose 納入衍生 context。再用 AAD（受驗證但不加密的附加資料）綁定資源、用途和對應格式版本，降低跨房間或跨用途誤用風險。AAD 不是秘密，也不會自動提供防重播。

傳輸協定與持久資料要有各自版本：不要因 WebSocket 協定升級而讓舊快照無法解開。若很多 client 共用一把 key，nonce 的碰撞風險要按這把 key 的總加密次數評估；random IV 不是數學上的唯一值。大規模或長生命週期系統要設定加密用量上限、輪替策略，或設計隔離的 sender key／nonce 空間。

3. 錯鑰、重播與恢復各自處理

在改動本地畫布前，以綁定 room 與 generation 的加密 key-check 驗證 key。驗證失敗就保留使用者原有內容；key-check 只是 client 的可讀性確認，不能取代伺服器授權，也不能只因伺服器「存有 verifier」就認定某人知道 key。

即時通道需要訊息識別與有界重播偵測；快照需要 revision／衝突契約。AEAD 只能證明密文有效，無法證明它是最新版本。若威脅模型包含惡意 storage 回滾，還需要可信的最新狀態錨點或可驗證歷史；單靠伺服器宣告 revision 不夠。重連時先解密有效快照，再合併遠端更新；不要讓錯鑰被誤判為空房間。

4. 撤銷與資料恢復必須成為產品行為

把 Bob 從 ACL 移除，只能阻止後續 API 存取，無法收回他已經拿到的 K。若要隔離未來內容，必須產生新的獨立金鑰，只交給留下來的成員，切換世代並中止舊連線。單純增加 generation 或換公開 salt，但仍沿用 Bob 知道的 root key，並不能達成密碼學撤銷。

舊金鑰仍能解開舊密文；輪替不會抹掉 Bob 已下載的資料。既有資料要保留時，需由可信 client 遷移／重新加密，設計好中途失敗與雙世代切換；若選擇重設清空，就要明白告知資料會被移除。失去唯一 key 且沒有備份時，服務不能只靠重設密碼恢復內容。

保證到哪裡，在哪裡停止

情境此 pattern 的保證與限制
資料庫或被動 relay 觀察者沒有 key 時不能解開加密內容；仍看得到外層 metadata、大小、時間。
密文被修改GCM 驗證會失敗；服務仍可能刪除、延遲或重播有效資料。
完整分享連結外洩解密能力外洩。若另有 ACL，可限制取資料的入口；不能讓已知 key 自動失效。
惡意成員或失陷裝置端點已能讀明文；不保護使用者截圖、匯出、轉傳或偽造共享-key 訊息。
前端 bundle、XSS 或供應鏈遭竄改惡意 JavaScript 可讀取 key 與明文。網頁版 E2EE 仍依賴程式碼交付的信任。

CSP、減少第三方腳本與保護部署流程可降低 code delivery 的風險，但不能把它變成「即使能改寫網頁程式的人也無法讀取內容」。同樣地，雲端傳輸 E2EE 不代表下載的 JSON、PNG、SVG 或瀏覽器本地儲存自動加密；這些出口需要獨立盤點。

什麼時候值得選，什麼時候換一種方案

當內容應只由參與者解讀、可以透過另一條通道分享秘密、client 能負擔合併與渲染，而且團隊接受金鑰遺失與分享連結外洩的後果時，這個 pattern 很適合白板、私密文件或臨時共享空間。它避免為臨時參與者先建一整套公開金鑰目錄，交換的是較粗的成員撤銷能力。

  • 選 HTTPS + 伺服器管理金鑰：伺服器必須做全文搜尋、內容審查、AI 處理或客服恢復，而使用者接受服務可讀內容。這是更簡單的可信伺服器模型，但不是同一種 E2EE 保證。
  • 選每位使用者的金鑰封裝：需要帳號導向分享、多裝置恢復與頻繁成員調整，可用成員公鑰封裝資料金鑰；要承擔裝置註冊、身分驗證、撤銷與恢復協定。這也不會自動帶來前向保密。
  • 不要只用單一長期房間 key：若要求洩漏今天的 key 仍不能解開過去錄下的訊息，或要求成員頻繁變動下的前向保密，應評估成熟群組加密協定，不要將此最小模式當作完整安全通訊協定。

可從 asset-crypto.ts、relay-client.ts 與 room-link.ts 追到本專案的協作實作。將這些用途隔離、授權與錯鑰防護視為產品化設計；Excalidraw 則提供了共享秘密、client 加密與不透明 relay 的具體參考。

設計時先回答三件事：誰應能讀明文、誰有權取得或寫入密文、金鑰遺失或成員離開後如何處理。這三個答案決定你需要簡單的 capability link、額外的 ACL，還是更完整的金鑰管理協定。
