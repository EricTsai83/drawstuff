Plan 10「最佳實踐評估」白話完整解說

這份文件重新解釋先前報告裡「最佳實踐評估」那一段：哪些做法是業界公認的正確做法、 哪些是明知不是教科書標準、但刻意選擇的取捨，以及三輪 AI 交叉審查到底修掉了什麼。 看完你應該能自己判斷「這次實作是不是最佳實踐」。

先建立三個名詞，後面會一直用到：
Upstream（上游）
Excalidraw 官方專案本身（npm 套件 @excalidraw/excalidraw@0.18.1 與它的原始碼）。我們的程式碼建立在它之上。
Adapter（轉接層）
這次寫的 reconcile.ts。它是 Drawstuff 與 Excalidraw 之間唯一的「窄門」：所有跟引擎有關的操作都必須走這裡。
Tracker（變更追蹤器）
記錄「哪些元素已經送給其他協作者了」的小帳本。有了它，你動一個方塊時只需要送那一個方塊，而不是整張 10,000 個元素的畫布。

第一部分：四項「符合最佳實踐」的做法

最佳實踐 1不重寫引擎的演算法，用「差異測試」證明

白話：兩個人同時改同一個方塊，最後聽誰的？這個「衝突裁判規則」是 Excalidraw 寫好的 （reconcileElements）。我們只包一層薄薄的外殼去呼叫它，一行裁判邏輯都不自己寫。

為什麼這是最佳實踐？如果自己再寫一套「差不多的」合併規則，會發生兩件事： （1）你的規則和引擎的規則在邊角情況下裁決不同 → 兩個使用者的畫面永久對不上； （2）Excalidraw 一升級，你的復刻版就過時了，而且沒有任何測試會告訴你。

那怎麼證明外殼沒有偷偷改變行為？用「差異測試」（differential testing）： 準備 16 組固定劇本（誰的版本新、誰刪除了元素、誰正在編輯中……），每組劇本同時餵給兩條路：

同一組輸入本地元素 + 遠端元素
➜
路徑 A直接呼叫 Excalidraw 原函式
＝?
路徑 B呼叫我們的 adapter
➜
逐欄位比對結果必須 100% 相同

只要 adapter 哪天「多做了一點事」，測試立刻紅燈。這就是「不是用信任、是用測試」的意思。

最佳實踐 2失敗方向設計：壞掉時「寧可重送、絕不遺失」

白話：分散式系統一定會出錯——網路斷線、佇列塞滿、時機不巧。 好的設計不是「假裝不會出錯」，而是規定出錯之後往哪邊倒。這裡的規定是： 任何意外都只能造成「同一筆變更多送一次」，永遠不能造成「有一筆變更沒送出去」。

多送一次（重送）＝ 無害

接收端的合併是「冪等」的：同一筆資料收兩次，結果跟收一次完全一樣 （版本相同 → 裁判規則判定為無變化）。頂多浪費幾百 bytes 流量。

少送一筆（遺失）＝ 災難

你畫的東西別人永遠看不到，而且沒有任何錯誤訊息。 兩邊畫面默默分岔，使用者只會覺得「這協作功能怪怪的」。

後面第三部分會看到：三輪審查修掉的三個 bug，全部都是「某個罕見時序下會變成遺失」的漏洞。 修完之後「只會重送、不會遺失」從大致成立變成結構上必然成立。

最佳實踐 3升級絆線（tripwire）：讓「升級 Excalidraw」不可能靜默出錯

白話：絆線就是綁在門口的細繩——小偷（行為改變）一進來就會絆倒觸發警報。這次埋了三條：

  • 版本絆線：測試會讀取實際安裝的 Excalidraw 版本，跟測試資料裡記錄的 0.18.1 比對。 升到 0.19 的那一刻，測試直接失敗，逼你重新審核。
  • 行為絆線：16 組劇本的「正確答案」被釘死在檔案裡。如果新版 Excalidraw 改了裁判規則 （例如平手時改成聽另一邊的），比對立刻失敗。
  • API 表面絆線：測試釘死了 adapter 對外只暴露 5 個函式。誰想偷偷加一個「方便的」直通引擎出口，測試失敗。

為什麼重要？依賴升級最可怕的不是「編譯錯誤」（那個很好處理），而是「編譯過了、行為變了、沒人發現」。 絆線把後者轉換成前者。

最佳實踐 4效能量測方法論：可重現、看 p95、只在校準過的機器上當門檻

  • 固定劇本：永遠用同一個 1,000／10,000 個元素的假畫布來量。下次有人改了程式，數字可以直接比。
  • 暖身 + p95：先跑 5 次不計分（讓 JavaScript 引擎「熱機」），再跑 30 次取第 95 百分位數—— 看「最差的正常情況」，而不是被平均值美化。
  • 兩種斷言分開：結構性保證（動 1 個元素只序列化 1 個元素、抽取時零複製）在任何電腦上都強制檢查； 速度門檻（例如 p95 ≤ 2ms）只在文件記錄的那台基準機器上強制——因為同一段程式在慢的 CI 機器上跑出 3ms 不代表程式變慢了。把速度門檻無條件掛在 CI 上是常見的反模式（flaky test 之源）。

第二部分：三個「有意識的取捨」——不是教科書標準，但有理由

「取捨」的意思是：我知道有一個更「純正」的做法，但它的代價比好處大，所以刻意不選它，並且把風險寫下來、加上防線。

取捨 1型別上的「善意謊言」：localState as AppState

背景：Excalidraw 的合併函式簽名要求傳入完整的 AppState——一個有幾十個欄位的大物件 （縮放倍率、主題色、選取狀態、開了哪個對話框……）。但去讀它的原始碼會發現：它實際上只讀其中 3 個欄位 （「這個元素是否正在被輸入文字／被縮放／正在畫」——正在操作中的元素本地必須贏，不能被遠端蓋掉）。

教科書做法

照簽名要求，讓呼叫者傳完整 AppState。型別 100% 誠實， 但未來的協作模組被迫隨身攜帶整包編輯器狀態，測試也得先造出一個巨大假物件。

實際選擇

對外只要求那 3 個欄位，內部用 as AppState 告訴 TypeScript「相信我」。 介面乾淨得多，但這是一句編譯器驗證不了的斷言。

風險：如果未來某版 Excalidraw 開始讀第 4 個欄位，TypeScript 不會報錯——那個欄位會默默是 undefined。

防線：（1）程式碼註解標明了 upstream 原始碼的檔案與行號，說明「只讀 3 個欄位」的證據出處； （2）第一部分的版本絆線會在升級時強制重新人工核對這件事；（3）差異測試涵蓋了這 3 個欄位各自生效的劇本。

取捨 2測試裡的 as unknown as ... 強制轉型

背景：Excalidraw 用了一種叫 branded types（烙印型別）的技巧： 某些型別除了資料形狀，還帶一個看不見的「官方印章」，宣告「這個元素是引擎親手做的」。 問題是——只有引擎內部能蓋這個章。測試要手工捏一個假元素來餵，形狀完全正確，但拿不到章， 只能用 as unknown as OrderedExcalidrawElement 硬轉。

為什麼可接受？（1）只出現在測試的資料工廠，正式程式碼（src/）沒有這種轉型； （2）去看 Excalidraw 自己的測試，它們也是同樣做法——這是烙印型別生態的固有限制，不是我們的偷懶。

取捨 3帳本規則的一個細節：「同版本」時允許覆寫

背景：tracker 的帳本有一條保護規則：「舊資料不能蓋掉新資料」（版本 2 的遲到記帳不能蓋掉版本 3）。 那版本相同但內容識別碼不同時要不要允許覆寫？兩個選項各有一個壞情況：

選項 A：同版本一律拒絕

更「嚴格」，但存在一種邊角狀態：帳本記的和畫布上的永遠差一個識別碼 → 每次檢查都覺得「有變更」→ 無限重送迴圈，永遠停不下來。

選項 B：同版本允許覆寫（實際選擇）

最壞情況是多回聲一次：多送一筆對方其實已經有的資料， 對方的裁判規則判定無變化，下一輪就安靜了。會自我痊癒。

判斷依據：「永不停止的迴圈」比「多送一次就好」嚴重得多。這也和 Excalidraw 官方的整體哲學一致—— 它甚至容忍更大的誤差（見下一部分結尾）。

第三部分：三輪審查的演進——同一個 bug 家族被連續抓了三次

這部分是原報告裡最難懂、也最有價值的段落。核心問題只有一個：
「哪些元素已經送出去了」這本帳，到底該在什麼時候、用什麼資料來記？
記帳時機錯 → 遺失；記帳資料錯 → 也遺失。三輪由 GPT-5.6 Sol 執行的交叉審查，每輪都在更刁鑽的時序下找到一個洞。

第 1 版樂觀記帳：「抽出來的當下」就記帳 → 送失敗時掉資料

第一版模仿 Excalidraw 官方 app 的做法：從畫布抽出變更清單的同時，就在帳本記下「已送出」。

  • 你把方塊改成版本 2
  • 系統抽出變更清單〔方塊 v2〕，並同時記帳：「v2 已送」
  • 網路層拒絕這次傳送（斷線／佇列滿）——但帳已經記了
  • 下一輪檢查：「帳上寫 v2 已送」→ 認為沒有東西要送 → 你的修改永遠傳不出去

審查裁決：接受。修法：拆成兩階段——抽取（extract）不記帳，傳送成功後才呼叫 commit 記帳。 送失敗就不 commit，下一輪自然重抽重送。順帶注意：忘記 commit 的後果是「多送」，不是「遺失」——連 API 的誤用方向都是安全的。

第 2 版兩階段有了，但 commit 時「重新去讀」一個會被就地修改的物件

修完第 1 版後，commit 記帳的資料是當下重新從元素物件上讀的版本號。 問題：Excalidraw 是就地修改（in-place mutation）元素物件的——同一個物件，版本號會直接在原地跳動。

  • 抽出方塊 v2，序列化成封包、送出（網路上跑的是 v2）
  • 就在 commit 之前，一個重入的畫布更新把同一個物件就地改成 v3
  • commit 執行：去物件上讀版本 → 讀到 v3 → 帳本記「v3 已送」
  • 但網路上只送過 v2！下一輪檢查認為 v3 已送 → v3 這筆修改遺失

審查裁決：接受。修法：抽取的當下就把每個元素的識別資料（id＋版本＋識別碼）拍一張不可變的快照， commit 永遠寫快照、絕不重讀活物件。

第 3 版快照存在「全 tracker 共用的一格」裡 → 兩個批次會互相覆寫

第 2 版的快照放在 tracker 身上的一個共用 Map（每個元素 id 一格）。第三輪審查指出：一格不夠。

  • 批次①抽出方塊 v2（快照格寫入 v2），封包送出但回應很慢，commit 被延遲
  • 物件就地變成 v3；批次②抽出 v3——快照格被覆寫成 v3
  • 批次①的延遲 commit 終於執行：它手上的物件參照現在顯示 v3，跟格子裡的 v3「對上了」→ 記帳 v3
  • 但批次①實際送出的是 v2 → v3 又遺失了（另外還有兩個較小的洞：帳本可能被遲到的 commit 蓋回舊值造成回聲、快照格永遠不清理會累積記憶體）

審查裁決：三項全接受。最終修法用一個設計同時解決三個洞——批次把手（batch handle）：

// 之前：抽取回傳陣列，commit 是 tracker 上的共用方法
const delta = tracker.extractChangedElements(scene);
send(delta);
tracker.markElementsSent(delta);   // ← 讀共用格，會被別的批次污染

// 之後：每個批次自帶自己的快照和自己的 commit 按鈕
const batch = tracker.extractChangedElements(scene);
send(batch.elements);
batch.markSent();                  // ← 只會寫「這個批次抽取當下」的快照
防護 1：批次快照快照鎖在批次內部，別的批次碰不到 → 互相覆寫在結構上不可能
防護 2：單調性檢查帳本已有更新的記錄時，遲到的舊 commit 直接跳過 → 不會倒退
防護 3：世代編號重新加入房間（reset）後，舊時代的批次 commit 一律無效 → 舊狀態不污染新連線

快照跟著批次物件一起被垃圾回收，記憶體累積問題也順帶消失。每個修法都有一個直接重演該失敗時序的測試釘住。

結論為什麼說最終版「優於 Excalidraw 官方 app 自己的實作」？

要分清楚兩件事：

  • 合併演算法（誰贏誰輸的裁判規則）：100% 沿用 Excalidraw，我們刻意一個字都不改。這部分不存在「優於」的問題。
  • 外圍的記帳機制（決定哪些元素要送出去）：Excalidraw 官方 app 用的就是上面「第 1 版」的樂觀記帳—— 送失敗一樣會掉資料。它的補救方式是每 20 秒把整張畫布全量重送一次，用蠻力把洞蓋掉（畫布大時很浪費頻寬）。 我們的版本經過三輪審查後，是結構上保證不掉資料，不需要靠定時全量重送兜底。
